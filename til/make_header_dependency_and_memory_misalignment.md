# ヘッダーファイル変更時に `make` が再コンパイルしない理由とメモリ破壊のメカニズム

## 📌 概要 (TL;DR)

C/C++ プロジェクトにおいて、ヘッダーファイル (`.h`) で構造体の定義を変更した後に `make` を実行しても、一部のオブジェクトファイル (`.o`) が再コンパイルされずに**古い状態で放置される**現象が発生した。

これにより、新旧のオブジェクトファイル間で**構造体のメモリレイアウト（変数のオフセット位置）の不一致**が生じ、変数の値が化ける・初期値が不正になる等の致命的なバグが引き起こされた。

---

## 🔍 なぜ `make` は再コンパイルを行わなかったのか？

### 1. `make` の判定基準は「タイムスタンプ（更新日時）」のみ
`make` コマンドは高速化のために、依存先ファイル（ソースコード）と生成物（`.o`）の**最終更新日時（タイムスタンプ）**を比較して再コンパイルの要否を判断している。

一般的な Makefile のルール:
```makefile
%.o: %.c
	$(CC) $(CFLAGS) -c $< -o $@
```
このルールは `make` に対して **「`foo.o` は `foo.c` の更新日時だけを見て判断しろ」** と指示している。

### 2. `make` は C言語の `#include` を理解しない
Cコンパイラ (`gcc` や `clang`) は `#include "header.h"` を解釈してヘッダーを読み込むが、**ビルドツールである `make` は `.c` ファイルの中身をパースしない**。

そのため、`Makefile` に明確な依存関係が書かれていない限り、`make` は `.h` と `.c` / `.o` の関係性を知ることができない。

### 3. 今回起きた不整合のタイムライン
1. `codexion.h` で `t_Dongle` 構造体に新しいメンバ (`cooldown_end_time`) を追加した。
2. `codexion.c` と `codexion.h` を保存して `make` を実行した。
3. **`make` の判断**:
   - `codexion.c`: 更新日時が新しい ➔ **再コンパイル実行 (`codexion.o` 更新)**
   - `dongle.c`: 編集していない（更新日時が古い） ➔ **再コンパイル省略 (`dongle.o` は古いまま)**
4. 結果として、**新しい構造体レイアウトを持つ `codexion.o`** と **古い構造体レイアウトを持つ `dongle.o`** がそのままリンクされた。

---

## 💥 メモリレイアウトの不一致 (Struct Offset Misalignment)

新旧の `.o` ファイルが混在してリンクされると、構造体メンバのメモリ上の位置（オフセット）がズレる。

```
[旧 dongle.o が書き込むメモリ構造]
+-------+--------------------+-----------+
| int i | pthread_mutex_lock | bool avail| ...
+-------+--------------------+-----------+
  i = 1                       avail=true

[新 codexion.o が読み出そうとするメモリ構造]
+-------+--------------------+-----------+---------------------+
| int i | pthread_mutex_lock | bool avail| long cooldown_time  |
+-------+--------------------+-----------+---------------------+
```

`dongle.o` がメモリに書き込んだデータのアライメントやパディングのズレにより、`codexion.o` 側から読み出すと、別の変数の値（例: `i = 1`）やパディングバイトが `cooldown_end_time` や `available` の位置に重なってしまった。

その結果、初期状態であるにもかかわらず：
- `available` ➔ `0` (`false`)
- `cooldown_end_time` ➔ `1`

という怪現象（メモリ化け）が発生し、処理が停止した。

---

## 🛠️ 対策・解決策

### 対策 1: ヘッダーファイルを依存関係に明記する（手動）
`Makefile` のコンパイルルールに `.h` ファイルを追加する。

```makefile
%.o: %.c codexion.h
	$(CC) $(CFLAGS) -c $< -o $@
```
これで `codexion.h` が更新された場合、全 `.c` ファイルが自動的に再コンパイルされる。

### 対策 2: 自動依存関係生成オプションを使う（推奨）
コンパイラの機能を使って、`#include` されているヘッダーの依存関係リスト (`.d` ファイル) を自動生成させる。

```makefile
CFLAGS = -Wall -Wextra -Werror -pthread -MMD -MP
SRCS   = main.c dongle.c codexion.c ...
OBJS   = $(SRCS:.c=.o)

-include $(OBJS:.o=.d)
```
- `-MMD`: ソースが依存するヘッダー情報を記載した `.d` ファイルを出力する。
- `-MP`: ヘッダーが削除された場合のエラーを防ぐダミーターゲットを作成する。
- `-include`: 生成された `.d` ファイルを Makefile に取り込む。

### 対策 3: 構造体やヘッダーを変更した時は `make clean && make`
ヘッダーファイルやビルド設定を変更した後は、常に `make clean` で古いオブジェクトファイルを完全に一掃してから再ビルドする習慣をつける。

---

## 📝 学び・訓言
- **「`.h` の変更は `.c` を直接触っていなくても全再コンパイルの対象である」**
- 原因不明のメモリ化けや初期値の異常が発生した時は、まず `make clean && make` を試す。
